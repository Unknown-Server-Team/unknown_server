# Unknown Server API Documentation - v1

## Overview

This document describes the v1 API endpoints of Unknown Server. The full, machine-readable specification is served at `/api/docs.json` and rendered by Swagger UI at `/api/docs`.

## Authentication

Protected endpoints require a JWT obtained from the register or login endpoint, sent as a Bearer token:

```http
Authorization: Bearer <token>
```

See the [Authentication Guide](../authentication.md) for the full flow.

## Versioning

Endpoints are versioned in the path (`/api/v1/...`). The optional `Accept-Version` header is checked on every `/api` request, defaults to `v1`, and an unsupported value is rejected with `400`:
```http
Accept-Version: v1
```

## Common Response Codes

| Code | Description |
|------|-------------|
| 200  | Success |
| 201  | Created |
| 400  | Bad Request |
| 401  | Unauthorized |
| 403  | Forbidden |
| 404  | Not Found |
| 409  | Conflict |
| 429  | Too Many Requests |
| 500  | Internal Server Error |

## Rate Limiting

All `/api/v1` endpoints share a limit of 60 requests per minute per IP. Stricter limits apply to:
- Login: 5 requests per 15 minutes
- Registration, forgot password and reset password: 3 requests per hour
- Profile updates (`PUT /api/v1/users/{id}`): 5 requests per 15 minutes

## Endpoints

### Authentication

#### POST /api/v1/auth/login
Authenticate a user and receive an access token.

**Request Body:**
```json
{
  "email": "string",
  "password": "string"
}
```

**Response:**
```json
{
  "token": "string",
  "user": {
    "id": "number",
    "email": "string",
    "name": "string",
    "email_verified": "number (0 or 1)"
  },
  "expiresIn": "number"
}
```

Other authentication endpoints: `POST /auth/register`, `GET /auth/me`, `GET /auth/verify-email/{token}`, `POST /auth/forgot-password` and `POST /auth/reset-password/{token}`.

### Role Management

Admin-only endpoints: `GET /auth/roles`, `GET /auth/user/{id}/roles`, `POST /auth/user/{id}/roles/{role}` and `DELETE /auth/user/{id}/roles/{role}`. See [Roles and Permissions](../roles-and-permissions.md).

### User Management

#### GET /api/v1/users
List users. Requires a verified account with the `admin` role.

**Query Parameters:**
- page (number, default: 1): Page number
- limit (number, default: 10, max: 100): Items per page

**Response:**
```json
{
  "success": true,
  "data": [{
    "id": "number",
    "email": "string",
    "name": "string",
    "email_verified": "number (0 or 1)",
    "created_at": "string",
    "updated_at": "string"
  }],
  "pagination": {
    "page": "number",
    "limit": "number",
    "total": "number",
    "pages": "number"
  }
}
```

Users do not include roles; fetch them from `GET /api/v1/auth/user/{id}/roles`.

#### GET /api/v1/users/{id}
Get one user as `{ "success": true, "data": {...} }`. Users may read their own record; admins may read any.

#### PUT /api/v1/users/{id}
Update `name` and/or `email`. Users may update their own record; admins may update any.

#### DELETE /api/v1/users/{id}
Delete a user. Requires a verified account with the `admin` role.

### System

- `GET /api/v1/health` - Health status and application version
- `GET /api/v1/metrics?period=hour|day|week` - Performance metrics
- `GET /api/v1/routes` - Registered routes

## WebSocket

The WebSocket server shares the HTTP port and accepts connections on any path:
```text
ws://server:port/
```

Messages are JSON objects with a `type` field:

| Type | Fields | Description |
|------|--------|-------------|
| auth:authenticate | token | Attach a user to the connection |
| join | room | Join a room |
| leave | room | Leave a room |
| broadcast | data, room | Send data to a room, or to everyone without a room |
| event | event, data | Run a registered event handler |

Registered event handlers are `auth:roleChange` and `auth:permissionChange`, which require the `role:write` and `permission:write` permission names respectively.

## Error Handling

Error responses always contain an `error` message. Depending on the endpoint they may also include `success: false` and a `details` object that maps field names to lists of validation messages:
```json
{
  "success": false,
  "error": "string",
  "details": {
    "field": ["string"]
  }
}
```

## Security Considerations

1. Always use HTTPS in production
2. Keep `JWT_SECRET` long and private
3. Validate all inputs on the client as well
4. Handle errors gracefully

## Example

```bash
curl -H "Authorization: Bearer $TOKEN" "https://your-domain.com/api/v1/users?page=1&limit=10"
```
